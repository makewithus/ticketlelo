# Creator Campus Ambassador Program — Data Architecture & Migration Guide

## 1. Overview & Dual-Model Compatibility Architecture

TicketLelo transitioned from a single-event legacy commission system (`ambassadors` keyed by `userId`) to an enterprise-grade multi-program Creator Campus Ambassador architecture with immutable double-entry points ledgers, transactional referral code reservations, and multi-tenant isolation.

**Zero Data Loss Guarantee**: All legacy ambassador profiles, commission records, event links, tickets, orders, and payment records are preserved with 100% backward compatibility.

---

## 2. Firestore Collections Schema Comparison

### 2.1 Legacy Schema (Maintained & Preserved)
* **`ambassadors/{ambassadorId}`**:
  - Legacy document ID: `userId` (single-program restriction).
  - Metrics: `clicks`, `paidOrders`, `attributedRevenue`, `commissionEarned`.
  - Fallback role: `role: "ambassador"` in `users` collection.
* **`ambassadorCommissions/{commissionId}`**:
  - Currency-based commission ledger records.

### 2.2 Modern Schema (Creator Campus Architecture)
* **`ambassadorPrograms/{programId}`**:
  - `name`: string (e.g. "PRAROHA 2027 Campus Ambassador Network")
  - `organizerId`: string (tenant owner UID)
  - `college`: string (campus / university focus)
  - `status`: `"draft"` | `"published"` | `"paused"` | `"archived"`
  - `pointsRules`: `{ basePointsPerTicket: number, paidMultiplier: number, milestones: array }`
  - `startDate`, `endDate`: ISO timestamp strings or null
  - `createdAt`, `updatedAt`: Firestore Timestamp
* **`programEvents/{relId}`**:
  - Many-to-many junction document between programs and events.
  - `programId`, `eventId`, `organizerId`, `enableReferral: boolean`.
* **`ambassadorApplications/{applicationId}`**:
  - Independent applications per program and user.
  - `programId`, `userId`, `organizerId`, `fullName`, `email`, `whatsappPhone`, `college`, `answers: object`, `status: "pending" | "approved" | "rejected"`, `createdAt`.
* **`programAmbassadors/{ambassadorId}`**:
  - Enrolled ambassador record for a specific program.
  - Document ID: `${programId}_${userId}` or autogenerated.
  - `programId`, `userId`, `organizerId`, `referralCode`, `totalPoints: number`, `status: "active"`, `enrolledAt`.
* **`referralCodes/{code}`**:
  - Globally unique index document where document ID is the normalized uppercase code (e.g. `ADIL-1042`).
  - Ensures O(1) atomic uniqueness without table scans.
  - `code`, `ambassadorId`, `userId`, `programId`, `organizerId`, `status: "active"`.
* **`pointsLedger/{entryId}`**:
  - Append-only immutable transaction log.
  - `idempotencyKey`: deterministic hash `pts_${programId}_${orderId||regId}_${ambassadorId}`.
  - `programId`, `ambassadorId`, `userId`, `eventId`, `orderId`, `points: number` (+/-), `type`, `reason`, `createdAt`.
* **`ambassadorRewards/{rewardId}`**:
  - 8 standard reward types (merchandise, vip_pass, certificate, mentorship, cash_voucher, gift_card, discount_coupon, custom).
  - `programId`, `organizerId`, `title`, `description`, `pointsRequired`, `totalInventory`, `remainingInventory`, `isActive`.
* **`ambassadorImports/{importId}`**:
  - Audit log of bulk CSV/XLSX imports with sanitized records.

## 3. Backward Compatibility & Resolution Strategy

1. **Referral Code Resolution (`lib/creator-campus/referral-registry.js`)**:
   - When resolving a referral code at checkout (`/api/create-order` or `/api/register-free`), the server first checks `referralCodes/{code}`.
   - If not found, it queries `ambassadors.where("referralCode", "==", code)`.
   - Legacy ambassadors are smoothly recognized and attributed.
2. **Ambassador Dashboard Resolution (`/api/ambassador/me`)**:
   - Queries `programAmbassadors` for modern enrollments.
   - If empty, inspects legacy `ambassadors` where `userId == uid`.
   - Existing ambassadors see their active status and referral code without interruption.
3. **Multi-Role User Linking**:
   - Organizers can serve as campus ambassadors without role collision or demotion.
   - Organizers maintain `role: "organiser"` or SuperAdmin claims with dedicated "Switch to Organiser Dashboard" navigation.

## 4. Database Indexing

The composite indexes defined in `firestore.indexes.json` support high-performance queries:
* `ambassadorApplications`: `(programId ASC, status ASC, createdAt DESC)`
* `ambassadorApplications`: `(userId ASC, createdAt DESC)`
* `programEvents`: `(programId ASC, enableReferral ASC)`
* `pointsLedger`: `(ambassadorId ASC, createdAt DESC)`
* `pointsLedger`: `(programId ASC, createdAt DESC)`
* `ambassadorRewards`: `(programId ASC, isActive ASC, pointsRequired ASC)`
* `programAmbassadors`: `(programId ASC, totalPoints DESC)`
